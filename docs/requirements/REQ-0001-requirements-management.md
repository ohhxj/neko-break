## 背景

Neko Break 的产品、设计、实现和 bug 修复想法分散在代码、设计文档和历史任务上下文里。用户希望建立一个专门的需求管理流程，让新需求可以被记录、评估、排期和跟踪，而不是只停留在提出它的那次对话中。

## 目标

建立一套轻量级需求管理系统，用来记录每个新增需求，把重要需求整理成可执行说明，支持优先级和路线图判断，并让产品规划与即时开发任务解耦。

## 用户场景

- 作为产品负责人，我希望每个新想法或 bug 修复想法都先被记录下来，这样后续不依赖记忆。
- 作为产品负责人，我希望每个需求都有优先级、工作量、依赖和验收标准，这样可以判断哪些需求应该现在做、下一批做或以后再做。
- 作为开发任务负责人，我希望从需求管理任务接收到清晰说明，这样开发时不用重新发现产品意图。

## 功能范围

- 创建 `docs/requirements/` 作为需求管理目录。
- 维护一个标准需求池，字段包含 ID、标题、来源、状态、优先级、工作量、依赖和验收摘要。
- 维护一个按 `Now / Next / Later` 分组的路线图。
- 提供可复用的需求说明模板。
- 把需求管理机制本身记录为第一个需求。
- 后续在这个专用任务中默认处理需求文档和排期，不直接改代码，除非用户明确要求开发。

## 非目标

- 本需求不要求改代码。
- 本需求不要求接入外部项目管理工具。
- 本需求不要求制定固定日期排期。
- 本需求不要求一次性把历史所有想法迁移进需求池，除非用户要求做更完整的产品审计。

## 交互注意点

当用户在这个任务中提出新功能、优化点或 bug 修复想法时，第一步应该先沉淀到需求池，再判断是否需要澄清、补详细说明、进入排期或拆到单独开发任务。

当未完成需求变多时，路线图应该按影响、紧急程度、工作量、依赖和风险重新排序，而不是按提出顺序开发。

## 技术注意点

仓库里已经有 `docs/design/` 和 `docs/superpowers/`。本需求单独增加 `docs/requirements/`，避免活跃需求管理覆盖历史规格、设计审计或视觉稿。

当前工作区存在与本需求无关的代码和资源改动。本需求只新增或修改 `docs/requirements/` 下的文档。

## 验收标准

- 假设仓库没有专门的需求管理目录，当本需求完成后，`docs/requirements/` 应该存在。
- 假设需要追踪新需求，当打开需求池时，应该能看到来源、描述/标题、状态、优先级、工作量、依赖和验收摘要字段。
- 假设需要对多个需求排期，当打开路线图时，应该能看到 `Now / Next / Later` 分组和优先级判断规则。
- 假设后续需求需要保持一致说明格式，当创建新需求说明时，`template.md` 应该提供背景、目标、用户场景、功能范围、非目标、交互注意点、技术注意点、验收标准和后续事项。
- 假设需求管理机制本身也要被跟踪，当查看需求池时，应该能看到 `REQ-0001`，并有详细说明和初始 P1 优先级。
